# Git / GitHub ハンズオン

このリポジトリは、あなたのteamの作業場所です。4〜6人で、Issueから変更・レビュー・マージまでを経験します。

## 最初に

1. [公開する情報について](PUBLICATION.md)を読み、[準備チェック](PRECHECK.md)を行います。
2. team内で担当A〜Fを決めます。4人ならA〜D、5人ならA〜E、6人ならA〜Fを使います。
3. このリポジトリの **Issues** タブで、`[1周目][担当A]`など自分の担当のIssueを開きます。`assignee:@me`で探す必要はありません。
4. 使わない担当のIssueは進めなくて構いません。2周目は講師の案内後に始めます。

## 作業の流れ

Issueを読む → mainを更新する → ブランチを作る → 編集・差分確認 → commit → push → PR → レビュー → 必要な修正 → 承認 → マージ → mainを更新する。

- 自分のPCで操作します。教える人は、相手の操作を代わりにせず言葉で助けます。
- mainには直接pushせず、自分の作業ブランチを使います。
- ブランチ名は `feature/Issue番号`。ファイルは `members/a.md` のように担当ごとに分けます。
- PRの取り込み先は、このteamのリポジトリのmainです。
- PRの説明の `Closes #番号` を実際のIssue番号に直します。IssueとPRの番号を混同しないようにします。

## レビュー相手

自分の次の担当のPRをレビューします。最後の担当はAのPRをレビューします。

| 人数 | レビューする向き |
|---|---|
| 4人 | A → B → C → D → A |
| 5人 | A → B → C → D → E → A |
| 6人 | A → B → C → D → E → F → A |

最初のヒントは2つです。

- このPRを取り込むと、Issueに書かれた仕事は終わる？
- そう判断するために、何を見たり試したりすればよい？

残りの確認観点はteamで考えます。PRの **Files changed** で差分を読み、必要な行にコメントします。**Start a review** を使った場合は、最後に **Finish your review / Submit review** で送信してください。確認が終わったら **Approve** で承認します。

修正が必要なら、PR作成者が同じブランチで編集し、commit・pushします。PRは新しく作り直しません。修正をpushすると以前の承認は取り消されるので、相手が再確認して承認します。講師が追加の指示を出す場合は、その案内を待ってからマージします。

相手の承認後、PR作成者が **Merge pull request → Confirm merge** でマージします。マージ後は次の順番で取り込みます。

```bash
git switch main
git pull --ff-only
```

仲間のファイルも手元にあることを確認します。2周目は新しいIssueと新しいブランチで進めます。

## 困ったら

まず `git status` で今の状態を確認し、team内で相談します。解決しない場合は、エラーが出ている画面をそのままにして講師・サポートを呼んでください。

`--force`を付けたpushや、作業を消す操作で解決しようとせず、まず相談してください。
